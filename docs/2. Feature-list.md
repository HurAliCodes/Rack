# Milestone 1.2 — Complete Feature List

## Goal

Define every feature that the application will support, grouped into modules.

This document serves as the **Product Requirements Document (PRD)** for the backend architecture. After completing this milestone, every feature should clearly identify:

* Which backend module owns it
* Which database tables it requires
* Which API endpoints it exposes
* Which AI service (if any) it uses

---

# High-Level Module Map

Rather than thinking in terms of pages, the application is designed around **business domains**.

```text
AI Digital Wardrobe
│
├── Authentication
├── Users
├── Wardrobe
├── Outfits
├── Dashboard
├── AI
├── Notifications
├── Media
├── Admin (Future)
└── System
```

This structure maps directly to a **feature-based backend architecture**, making the system easier to maintain, scale, and extend.

# Architecture Decision: Categories, Colors, Brands, Seasons, and Occasions

Before designing the database schema, the following architectural decisions are established.

## Categories

Use a **dedicated table** (or an enum during early development).

**Reason:**

Categories are controlled values that drive business logic and validation.

---

## Brands

Store as a **simple string field**.

**Reason:**

Users should be free to enter any brand. Creating a dedicated table adds unnecessary complexity with minimal benefit.

---

## Colors

Store:

* One normalized primary color
* Optional AI-generated color palette in the future

**Reason:**

This keeps searching efficient while allowing richer AI features later.

---

## Seasons

Use a **many-to-many relationship**.

**Reason:**

A clothing item can be appropriate for multiple seasons.

Example:

* Spring
* Autumn

---

## Occasions

Use a **many-to-many relationship**.

**Reason:**

One clothing item may suit multiple occasions.

Example:

* Casual
* Work
* Party

This design provides flexibility without unnecessary duplication.
